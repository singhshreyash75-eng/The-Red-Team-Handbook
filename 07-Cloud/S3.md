# S3

> Amazon S3 fundamentals, permissions, enumeration, public-access risks, and storage-security concepts for authorized AWS assessments.

## What is S3?

**S3 = Simple Storage Service**

Amazon S3 is AWS's object-storage service.

S3 stores:

```text
Objects
```

inside:

```text
Buckets
```

Conceptually:

```text
S3
 |
 +-- Bucket
      |
      +-- image.png
      +-- backup.zip
      +-- config.json
      +-- logs/
```

---

# Object Storage

S3 is **object storage**, not a traditional filesystem.

An object consists conceptually of:

```text
Key
Data
Metadata
```

Example:

```text
Bucket:
company-backups

Key:
database/prod.sql.gz
```

Together:

```text
s3://company-backups/database/prod.sql.gz
```

---

# Bucket Names

S3 bucket names are globally unique within the relevant AWS partition namespace.

Example:

```text
company-production-backups
```

A bucket belongs to an AWS account but its name cannot simply duplicate another existing bucket name in the same namespace.

Basic S3 interaction uses:

```bash

```


List objects:

```bash

```

Recursive listing:

```bash
aws s3 ls s3://<bucket> --recursive
```

Only access buckets and objects covered by the assessment authorization.

# Buckets and Objects

Hierarchy appears filesystem-like:

```text
bucket
 |
 +-- documents/
 |      |
 |      +-- report.pdf
 |
 +-- backups/
        |
        +-- db.sql
```

but internally:

```text
documents/report.pdf
```

is an object key.

The apparent folders are prefixes.

# S3 Permissions

S3 access can be influenced by multiple mechanisms:

```text
IAM Policies
Bucket Policies
Access Control Lists
Access Points
Block Public Access
Organization controls
```

Therefore:

```text
"User policy doesn't allow it"
```

is not always enough information to understand the complete authorization model.

---

# IAM Policy

An IAM identity may receive S3 permissions.

Conceptually:

```text
IAM Principal
     |
IAM Policy
     |
     v
S3 Bucket
```

Common S3 actions include:

```text
s3:ListBucket
s3:GetObject
s3:PutObject
s3:DeleteObject
```

---

# ListBucket vs GetObject

Important distinction:

```text
s3:ListBucket
```

allows listing object keys in a bucket.

Whereas:

```text
s3:GetObject
```

controls reading objects.

Therefore it is possible conceptually to have:

```text
GetObject
```

without:

```text
ListBucket
```

This means inability to list a bucket does not necessarily prove inability to retrieve a specifically known object.

---

# PutObject

```text
s3:PutObject
```

allows writing objects.

Write access can be security-sensitive.

Potential impacts depend on bucket purpose.

Examples:

```text
Application assets
Configuration
Deployment artifacts
Static websites
Backups
Logs
```

---

# DeleteObject

```text
s3:DeleteObject
```

permits object deletion.

This affects:

```text
Availability
Integrity
Recovery
```

Versioning and retention controls can reduce impact.

---

# Bucket Policies

A **bucket policy** is a resource-based policy attached to the bucket.

Conceptually:

```text
Bucket
 |
Bucket Policy
 |
 +--> Principal
 +--> Action
 +--> Resource
 +--> Condition
```

Bucket policies can grant access across accounts or to services.

---

# Public Bucket Concept

A bucket/object becomes publicly accessible when authorization allows unauthenticated/public access.

Conceptually:

```text
Internet User
     |
     v
S3 Object
```

Public access is not inherently a vulnerability.

Some buckets intentionally host:

```text
Public websites
Public datasets
Static assets
Downloads
```

The security question is:

```text
Was public access intended?
```

---

# Block Public Access

AWS provides:

```text
S3 Block Public Access
```

as a guardrail against unintended public exposure.

It can be configured at:

```text
Account level
Bucket level
```

Review it during authorized security assessments.

---

# ACLs

S3 historically supports:

```text
Access Control Lists
```

ACLs can grant permissions to accounts or predefined groups.

Modern AWS security designs generally favor:

```text
IAM policies
Bucket policies
Object Ownership controls
```

over extensive ACL usage.

---

# Object Ownership

S3 provides Object Ownership controls that simplify ownership and ACL behavior.

Modern configurations often use:

```text
Bucket owner enforced
```

which disables ACL-based access control.

---

# Enumeration

First establish identity:

```bash
aws sts get-caller-identity
```

Then:

```bash
aws s3 ls
```

If a bucket is known and authorized:

```bash
aws s3 ls s3://<bucket>
```

Always interpret results in context.

For example:

```text
AccessDenied
```

means the attempted action was denied.

It does not necessarily prove that every possible S3 action on that bucket is denied.

# Encryption

S3 supports encryption at rest.

Common approaches include:

```text
SSE-S3
SSE-KMS
```

### SSE-S3

AWS-managed S3 encryption keys.

### SSE-KMS

Uses AWS Key Management Service.

Conceptually:

```text
Object
  |
Encrypted
  |
KMS Key
```

KMS introduces another authorization layer.

An identity may need both:

```text
S3 permission
+
KMS permission
```

depending on configuration.

---

# KMS

**KMS = Key Management Service**

With SSE-KMS:

```text
Principal
    |
    +--> S3 permission
    |
    +--> KMS permission
```

Therefore:

```text
Can read S3 object
```

does not always mean:

```text
Can decrypt object
```

if required KMS access is unavailable.

---

# Versioning

S3 Versioning maintains multiple versions of objects.

Conceptually:

```text
report.txt
 |
 +-- Version 1
 +-- Version 2
 +-- Version 3
```

Benefits include:

```text
Recovery from accidental deletion
Recovery from overwrite
Improved resilience
```

---

# Object Lock

S3 Object Lock can provide retention controls.

Useful for:

```text
Backups
Compliance
Ransomware resilience
Audit data
```

It can prevent objects from being modified/deleted for a defined period depending on configuration.

S3 activity can be monitored through mechanisms including:

```text
CloudTrail

```

Logging is important for detecting:

```text
Unexpected reads
Bulk downloads
```

# Sensitive Data

Buckets commonly contain valuable information:

```text
Backups
Source artifacts
Logs
Configuration
Documents
Database exports
Credentials accidentally uploaded
Infrastructure templates
```

Therefore S3 exposure can become a data-security issue even without compute compromise.

---

# Secrets in Buckets

Never intentionally use ordinary S3 objects as an unmanaged credential store.

Prefer:

```text
AWS Secrets Manager
SSM Parameter Store
```

where appropriate.

Sensitive files accidentally found in storage might include:

```text
.env
config.json
credentials
backup files
private keys
```

Treat them according to the authorized assessment scope and data-handling rules.

---

# Static Website Hosting

S3 can host static websites.

Conceptually:

```text
Internet
    |
S3 Website Endpoint
    |
index.html
```

Public read access may therefore be completely intentional.

Do not report:

```text
Public S3 bucket
```

as a vulnerability without understanding its purpose and exposed content.

---

# Pre-Signed URLs

S3 can provide temporary access through:

```text
Pre-Signed URLs
```

Conceptually:

```text
Private Object
      |
Signed URL
      |
Temporary Access
```

A pre-signed URL should be treated as a temporary bearer credential for the permitted operation.

Anyone possessing a still-valid URL may be able to use the access it grants.

---

# Cross-Account Access

Bucket policies can permit another AWS account or principal to access resources.

Conceptually:

```text
Account A
   |
Principal
   |
   v
Bucket in Account B
```

Cross-account access should be intentionally scoped.

---

# Common Misconfigurations

Look for:

```text
Unintended public read
Unintended public write
Overly broad bucket policies
Overprivileged IAM
Sensitive data exposure
Leaked pre-signed URLs
Weak cross-account policies
Missing logging
Inadequate versioning
Excessive KMS permissions
Unnecessary ACLs
```

---

# Public Read vs Public Write

These have very different impacts.

## Public Read

Potentially affects:

```text
Confidentiality
```

## Public Write

Potentially affects:

```text
Integrity
Availability
Application behavior
```

Never treat them as equivalent findings.

# IAM + S3

Always connect S3 findings back to IAM.

Example:

```text
Developer
    |
s3:GetObject
    |
Backup Bucket
    |
Sensitive Backup
```

Another relationship:

```text
User
   |
CanModifyBucketPolicy
   |
Bucket
   |
CanChangeAccess
```

The second relationship may be more security-sensitive than simply reading an object.

---

# S3 + EC2

Cloud resources frequently interact.

```text
EC2 Instance
     |
IAM Role
     |
     v
S3 Bucket
```

If the EC2 application is compromised:

```text
Application
     ↓
EC2 Role
     ↓
S3 Permissions
```

The impact depends on the role's permissions.

---

# S3 + Lambda

Likewise:

```text
Lambda
   |
Execution Role
   |
   v
S3
```

Therefore serverless security depends heavily on IAM.

```text
Who owns the bucket?

Who can list it?

Who can modify the policy?

Is it intentionally public?

Does it contain sensitive data?

Is encryption enabled?

Which KMS key is used?

```

# Defensive Best Practices

Use:

```text
Block Public Access
Least-privilege IAM
Bucket policies with narrow principals
Encryption
Versioning
Object Lock where appropriate
CloudTrail
Access logging where appropriate
Regular access reviews
Sensitive-data discovery
```

Avoid:

```text
Wildcard principals
Unnecessary public access
Long-lived credentials
Sensitive secrets in buckets
Broad cross-account access
```

---

# Key Takeaway

Think of S3 security as:

```text
IDENTITY
    +
POLICY
    +
BUCKET
    +
OBJECT
    +
DATA
```

The most important distinction is:

```text
Bucket exists
      !=
Bucket is accessible
      !=
Bucket is public
      !=
Public access is unintended
```

Always determine:

```text
WHO can perform
WHAT action
on WHICH bucket/object
and whether that access
is INTENDED.
```
